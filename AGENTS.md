# Інструкції для Codex

## 1. Загальні правила роботи

- Працюй виключно в межах поточного проєкту та поставленого користувачем завдання.
- Перед внесенням змін ознайомся зі структурою проєкту, наявною архітектурою, стилем коду та реалізацією схожих функцій.
- Не внось зміни, які не стосуються поточного запиту.
- Не виконуй додатковий рефакторинг, перейменування, форматування або перебудову архітектури без прямої необхідності.
- Намагайся створювати мінімальний і сфокусований набір змін.
- Не змінюй наявну поведінку системи, якщо це прямо не передбачено завданням.

## 2. Робота з файлами проєкту

- Внось зміни безпосередньо в оригінальні файли поточного проєкту та в їхніх оригінальних директоріях.
- Не створюй копії проєкту, тимчасові клони, додаткові робочі дерева Git або дублікати файлів для реалізації змін.
- Не перенось файли до інших директорій без прямої вимоги завдання.
- Не змінюй файли поза поточною робочою директорією проєкту.
- Не видаляй і не перезаписуй зміни користувача, які не стосуються поточного завдання.
- Якщо у файлі вже є сторонні незавершені зміни, збережи їх та редагуй лише необхідні ділянки.

## 3. Робота з Git

- Працюй виключно на поточній вибраній гілці.
- Не перемикайся на інші гілки.
- Не створюй нові гілки.
- Не видаляй і не перейменовуй гілки.
- Не створюй коміти.
- Не додавай файли до Git staging area.
- Не виконуй merge, rebase, cherry-pick, revert, reset, restore, stash або clean.
- Не змінюй Git-конфігурацію, теги, remotes, hooks або інші службові дані репозиторію.
- Не виконуй push, pull, fetch, clone або будь-які інші операції взаємодії з віддаленим репозиторієм.
- Не відкривай pull request і не публікуй зміни.
- Не використовуй команди Git, які можуть змінити стан робочої директорії, індексу, гілок або історії репозиторію.

Дозволено використовувати лише read-only команди Git для аналізу поточного стану, наприклад:

- `git status`
- `git diff`
- `git log`
- `git show`
- `git blame`
- `git branch --show-current`
- `git rev-parse`

Якщо виконання завдання потребує перемикання гілки, завантаження даних із remote або іншої забороненої Git-операції, зупини роботу та повідом про це користувача.

## 4. Межі реалізації

- Реалізовуй лише те, що прямо зазначено в запиті користувача.
- Не додавай функціональність «про всяк випадок».
- Не змінюй публічні інтерфейси, API, структури даних або поведінку суміжних компонентів без необхідності.
- Не додавай нові production-залежності без явної згоди користувача.
- Використовуй наявні бібліотеки, утиліти, компоненти та патерни проєкту.
- За наявності кількох способів реалізації обирай найпростіший варіант, який узгоджується з поточною архітектурою.
- Якщо вимога неоднозначна і різні трактування можуть суттєво вплинути на результат, спочатку уточни її.
- Не вигадуй відсутні бізнес-вимоги.

## 5. Стиль і якість коду

- Дотримуйся наявного стилю коду, форматування, найменування та структури файлів.
- Не переформатовуй увесь файл, якщо зміни стосуються лише його невеликої частини.
- Код має бути зрозумілим, підтримуваним і відповідати практикам, які вже використовуються в проєкті.
- Уникай дублювання логіки, якщо в проєкті вже існує відповідна функція або утиліта.
- Обробляй помилки відповідно до наявних підходів проєкту.
- Не залишай мертвий код, тимчасові заглушки, налагоджувальні повідомлення або закоментовані фрагменти реалізації.
- Не додавай секрети, паролі, токени, ключі доступу або персональні дані до коду чи конфігураційних файлів.

## 6. Коментарі та документація

- Додавай описи для нових функцій, класів, методів, модулів і публічних інтерфейсів.
- Для публічних функцій використовуй прийнятий у проєкті формат документації: docstring, JSDoc, PHPDoc, XML documentation або відповідний аналог.
- В описах зазначай призначення функції, важливі параметри, результат виконання та можливі винятки або помилки, коли це доречно.
- Додавай внутрішні коментарі лише для складної або неочевидної логіки.
- Коментарі повинні пояснювати причину чи намір рішення, а не дослівно повторювати код.
- Не додавай зайві коментарі до очевидних операцій.
- Під час зміни поведінки оновлюй пов’язану документацію та наявні коментарі, якщо вони стали неактуальними.
- Мова нових коментарів має відповідати мові, яка вже переважає в кодовій базі. Якщо сталої практики немає, використовуй українську.

## 7. Перевірка змін

- Після реалізації перевір змінений код доступними локальними засобами.
- Запускай лише тести, перевірки типів, lint та форматування, що стосуються зміненої частини проєкту.
- Не запускай команди, які потребують доступу до віддаленого репозиторію або зовнішньої мережі.
- Не виправляй сторонні помилки тестів або lint, які не спричинені поточними змінами.
- Якщо перевірки неможливо виконати, чітко повідом причину.
- Перед завершенням переглянь diff і переконайся, що він містить лише зміни, необхідні для виконання запиту.

## 8. Спілкування

- Спілкуйся з користувачем українською мовою.
- Пояснюй виконані дії стисло та конкретно.
- Не стверджуй, що перевірка або тестування успішні, якщо вони фактично не виконувалися.
- Якщо виникла помилка або обмеження, повідом про це прямо.
- Перед виконанням потенційно руйнівної або незворотної дії обов’язково запроси підтвердження. За замовчуванням такі дії не виконувати.

## 9. Підсумок виконання

Після завершення кожного завдання надай:

1. Короткий опис реалізованих змін.
2. Перелік змінених файлів.
3. Перелік виконаних тестів і перевірок.
4. Інформацію про перевірки, які не вдалося виконати.
5. Відомі обмеження або потенційні ризики.
6. Підтвердження, що Git-гілка, історія, staging area та віддалений репозиторій не змінювалися.

## 10. Призначення та технологічний стек проєкту

- Проєкт є вебінтерфейсом конфігуратора продукту Lippert із вбудованою 3D-сценою PlayCanvas, переліком деталей, керуванням камерою та експортом моделі для перегляду в AR.
- Клієнтська частина побудована на React 19 і TypeScript. Збирання та dev-сервер виконує `@threekit-tools/treble-scripts`.
- Маршрутизація реалізована через `react-router-dom`, глобальний стан UI — через Redux Toolkit і `react-redux`.
- Стилі компонентів ізольовані у файлах `*.module.scss`; глобальні стилі містяться в `src/index.css`.
- 3D-рушій не входить до клієнтського bundle: опублікований PlayCanvas-проєкт завантажується під час виконання з CDN як ES-модулі, таблиця стилів і manifest.
- Серверна частина — CommonJS-застосунок Express у `server.js`. Вона роздає production-збірку, проксіює email-запити та приймає, оптимізує і зберігає GLB/USDZ-файли для AR.
- Основні формати коду: TypeScript/TSX для актуального клієнта, JavaScript/JSX для успадкованих Treble-компонентів і CommonJS для сервера.

## 11. Структура проєкту

- `src/index.tsx` — браузерна точка входу; монтує React у `#tk-treble-root`.
- `src/App.tsx` — корінь застосунку; підключає Redux Provider, ініціалізує атрибути продукту та запускає router.
- `src/router/` — таблиця маршрутів. `/` і `/:productId` відкривають конфігуратор, wildcard-маршрут — сторінку відсутнього продукту.
- `src/pages/` — композиція сторінок. Основна робоча поверхня збирається у `ConfiguratorPage`.
- `src/components/` — UI-компоненти конфігуратора. Компоненти `Treble/` є успадкованим набором JSX-компонентів і можуть використовувати API пакета `@threekit-tools/treble`; не змішуй їх без потреби з локальним адаптером атрибутів.
- `src/configurator/` — прикладний адаптер між Vivid Product API, метаданими варіантів і глобальним PlayCanvas API. Тут зосереджені кеш атрибутів, значення за замовчуванням і відповідність назв атрибутів ключам 3D-конфігурації.
- `src/services/productAttributes/` — клієнт і типи Vivid Product API; сервіс завантажує доступні option/geometry groups і кешує перетворений результат за product ID.
- `src/store/` — Redux store, slice, selectors і типи UI-стану конфігуратора.
- `src/hooks/` — адаптери до глобального `ConfiguratorAPI`, вибору деталей, зовнішньої datatable та стану камери.
- `src/modules/ar-module/` — ізольований AR-сценарій: експорт моделі з PlayCanvas, upload на Express API, QR-код або iOS Quick Look.
- `src/assets/` — локальні React-компоненти іконок.
- `public/` — HTML-шаблон і статичні файли клієнта.
- `server.js` — HTTP API та production static server.
- `treble-app/` — окремий мінімальний package manifest Treble; основні команди поточного застосунку визначені в кореневому `package.json`.
- `README.md`, `CLIENT_INTEGRATION_GUIDE.md` і `AR-PLAYCANVAS-API.md` — наявна функціональна та інтеграційна документація. Під час зміни відповідних контрактів перевіряй їхню актуальність.

## 12. Архітектура та потоки даних

### 12.1. Запуск клієнта

1. `src/index.tsx` створює React root.
2. `AppInit` викликає `initProductAttributes()` до формування початкового Redux-стану атрибутів.
3. `ProductAttributesService` отримує дані продукту `2669` з Vivid API; `mockAttributes.ts` об'єднує їх із локальним `attributeMetadataMap.ts`.
4. `ConfiguratorPage` монтує 3D-плеєр і пов'язані панелі керування.
5. `PlayCanvasPlayer` додає CDN stylesheet, manifest, import map та `index.mjs`, після чого очікує появи `window.ConfiguratorAPI`.

### 12.2. Синхронізація UI та 3D

- `window.ConfiguratorAPI` є головним контрактом керування опублікованою PlayCanvas-сценою: конфігурація, камера, outline/selection та annotations.
- `useConfiguratorAPI` опитує `window.ConfiguratorAPI` до готовності, читає початковий стан і підписується на його зміни. Компоненти не повинні дублювати цю логіку без необхідності.
- `useAttribute` керує локальним кешем атрибутів і через `playcanvasBridge.ts` перетворює доменні назви на ключі PlayCanvas.
- Redux slice зберігає UI-проєкцію атрибутів, статус обробки, номер camera stage і ознаку готовності API. Він не є повною копією стану PlayCanvas.
- Вибір деталі синхронізується через `ConfiguratorAPI.outline`; довідкові дані деталей окремо завантажуються з Vivid datatable `524` і збагачують дані модальних вікон.
- `productId` із маршруту визначає CDN-шлях PlayCanvas-продукту; без параметра використовується ID `2669`. ID PlayCanvas-проєкту за замовчуванням — `428`.

### 12.3. AR-потік

1. `useArExport` очікує глобальний `window.configurator` і паралельно експортує GLB та USDZ.
2. Клієнт надсилає обидва файли як multipart form-data на `POST /api/ar/upload`.
3. Express оптимізує GLB розміром від 5 MB, зберігає GLB, USDZ і JSON-метадані в локальній директорії `ar-models/`.
4. Сторінка `/ar/view/:id` спрямовує iOS у Quick Look, Android у Scene Viewer, а desktop-користувачу пропонує файли для завантаження.
- У dev-режимі клієнт на порту `5173` очікує AR backend на порту `8080`. Базову адресу можна перевизначити через `window.__AR_API_BASE__`.
- `ar-models/` є runtime-сховищем, створюється сервером автоматично й не належить до вихідного коду.

## 13. Зовнішні залежності та контракти

- Для повноцінної роботи клієнта потрібен мережевий доступ до Vivid API та CDN PlayCanvas. Не замінюй ці інтеграції моками або локальними ресурсами без прямої вимоги.
- Константи product/project IDs і URL наразі задані безпосередньо в `src/configurator/productInstance.ts`, `src/components/PlayCanvasPlayer/PlayCanvasPlayer.tsx` та `src/hooks/useDatatableParts.ts`.
- Глобальні об'єкти `window.ConfiguratorAPI` і `window.configurator` мають різне призначення: перший керує сценою, другий надає низькорівневий експорт GLB/USDZ. Не об'єднуй їхні типи чи життєві цикли.
- Express використовує `POSTMARK_TOKEN` для `/api/email`; секрет має надходити лише через середовище виконання.
- AR API записує файли на локальний диск і використовує внутрішній числовий лічильник ID. Ця реалізація не розрахована на кілька паралельних server instances або довговічне зовнішнє сховище.

## 14. Команди розробки та перевірки

- `npm start` — запустити клієнтський dev-сервер на порту `5173`.
- Для локального AR-сценарію запусти backend окремо з `PORT=8080`; команда `npm run serve` без цієї змінної використовує порт `80`.
- `npm run build` — створити production-збірку в `build/`.
- `npm run lint` — перевірити весь каталог `src/` через ESLint.
- `npx tsc --noEmit` — виконати перевірку типів без генерації файлів.
- `npm run format` змінює всі файли в `src/`; не запускай його для вузьких змін. За потреби форматуй лише явно змінені файли через Prettier.
- Автоматизованого test script у `package.json` немає. Для змін інтеграційного UI додатково перевіряй завантаження сцени, готовність глобальних API, синхронізацію контролів і cleanup після зміни product ID або unmount.

## 15. Проєктні правила внесення змін

- Зберігай межі між UI, адаптером `src/configurator/`, транспортним сервісом і зовнішнім PlayCanvas API.
- Нові звернення до конфігурації сцени проводь через наявний `useConfiguratorAPI` або `playcanvasBridge.ts`, залежно від того, чи потрібна реактивна підписка, чи одноразове оновлення атрибута.
- Під час додавання нового конфігураційного атрибута узгоджено онови тип стану API, mapping у `playcanvasBridge.ts`, метадані варіантів і початкову UI-проєкцію.
- Під час роботи з динамічними PlayCanvas-ресурсами зберігай cleanup глобальних об'єктів, script/link/importmap елементів і event listeners.
- Не вважай `MainLayout` активною оболонкою маршрутів без окремого підключення: поточна таблиця маршрутів рендерить сторінки безпосередньо.
- Не покладайся на `useCameraRotation` як на точне читання реальної камери, доки `USE_MOCK` має значення `true`.
- Не додавай згенеровані `build/`, runtime-каталог `ar-models/` або `tsconfig.tsbuildinfo` до змін вихідного коду.
